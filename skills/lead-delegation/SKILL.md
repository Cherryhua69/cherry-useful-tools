# 主导式委派

主导者核实现状、拆解任务、定稿文案、审查、验证并集成。Pi（GPT）实现代码、补必要的测试和代码注释、提供截图与结果。Codex CLI 做只读调研。用户决定产品方向、取舍、文案和是否推送。

委派与会话操作按 `codexhost-delegation` 和本机 `codexhost ... --help` 执行。

## 核实与决策

- 用户说“慢”“有问题”“想简化”时，先用实测或关键代码定位事实，再写任务。涉及其他部署或仓库时，核对实际配置及受影响范围。
- 大量阅读交给 Codex CLI。要求一页摘要、方案对比表和证据。项目结论附 `文件:行号`，外部结论附来源，并标明依据来自源码还是文档。
- 有产品取舍时，给两个选项，说明推荐及成本、风险和体验影响，等待用户决定。把用户的决定原话写进任务文件。概念问题直接解释。
- 文档、Skill 和变更记录由主导者撰写，同一规则在一处写全。文案、占位符、单行配置或少量断言直接处理。需要设计、跨包、新测试或涉及安全边界时，按任务说明委派。

## 写任务和派发

1. 在 scratchpad 按 [任务模板](references/task-template.md) 写 `task-<主题>.md`。
2. 小改动且文件互不重叠时用主工作区。大改动或并行任务可能冲突时，从集成分支当前提交为每项任务建独立分支和 worktree。用户指定隔离方式时按其要求。需要带入主导者未提交的前置改动时，先提交该部分，再从包含它的提交创建 worktree。
3. 用下列命令派发 Pi 任务，替换尖括号占位内容后按工具说明订阅完成通知。

   ```text
   codexhost delegate start --harness pi --cwd "<工作区路径>" --task-name "<短名>" --task "请阅读并完成任务文件 <绝对路径>。规格建好后直接继续实现。全程不提交，完成后按任务文件要求汇报。"
   ```

4. 收到完成通知后用 `thread read` 读取结果。遇到 `THREAD_BUSY` 时保留当前回合，把新增要求追加到任务文件的“补充”一节，等通知后用 `thread send` 提醒同一会话。补充说明只写本轮要改的范围。

## 审查与集成

1. 主导者按 [审查清单](references/review-checklist.md) 读 diff。问题编号发回同一会话，修改后再审。Pi 报告的检查适用于同一工作树状态时直接引用并标明来源；有遗漏、结果可疑或主导者改过代码时，补跑对应的聚焦测试。
2. 交付要求包含集成时，在对应工作区按项目约定提交，提交正文写清原因。项目没有约定时用 Conventional Commit。有 OpenSpec 变更时归档并校验该变更。使用 worktree 时用 `git merge --no-ff` 合回集成分支，解决过合并冲突时检查受影响包的类型。
3. 发现其他人的未提交改动时保留并报告。用户要求一起提交时，先通过修改时间确认编辑已结束，验证相关改动后单独提交。
4. 仅在用户要求时推送。推送到公开仓库前检查待推送内容中的凭据、服务器地址、私有仓库名、本机路径和临时目录。

汇报先写结论，再用表格列出交付、亲自验证的内容、Pi 报告的结果、未验证事项和待用户决定的内容。解释技术取舍时用用户能理解的具体影响。
